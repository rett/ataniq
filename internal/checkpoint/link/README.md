# Checkpoint witness link v2

The witness dials the home over TLS 1.3 with ALPN `ataniq-checkpoint/2`. At the home, construct a `NewEndpoint` with the home TLS identity, independently provisioned witness client certificate (DER), witness Ed25519 public key and expected epoch, the single enrollment slot and the witness source prefixes (`TrustSources`). On the home firewall, allow inbound connections to this listener only from those witness source prefixes. Run `Endpoint.Serve` on the home's listener. `Endpoint.Connect` takes the exact slot, home private key and process session private key. Its signed grant check can succeed before enrollment.

On the authority host, construct a `NewServer` with the witness TLS identity and signing public key, home address and TLS pin in a `Remote`, and the same enrollment slot. Run `Server.Poll(ctx, witness)` once. Run a separate Server for each home. Each connection carries a poll followed by one signed home request or an idle indication. The witness returns the result on the same connection. Cancellation stops polling. The home admits one ordinary call and reserves a second lane for receipt lookups. Competing calls receive ErrBusy before handoff.

Implementations check the provisioned key in `CheckHome` under the request context (including cancellation and shutdown), recheck the live grant while taking the read snapshot in `ReadHome`, and verify the signed claim or advance and current write grant as part of the transaction in `RawSubmit`. A successful mutation returns its committed receipt. A backend that loses certainty about commit returns `checkpoint.ErrUnknownOutcome`.

For owner calls, use `ServeOwner` on a private Unix-domain stream listener. Supply the administrative capability, its backend's witness evidence capability, the pinned SPKI fingerprint of the owner's client certificate and the administrator UID. Dial that endpoint with `Remote.Administration` and the matching TLS identity. The authenticated owner can read, settle, enroll, release and retire. Enrollment also carries the home's proof of possession.

## Framing and bounds

One connection carries one request. The four-byte unsigned big-endian length covers the entire payload. The payload starts with version byte 2 and a one-byte message kind. Mutation kinds also carry a fresh 32-byte delivery nonce before the fields. Each field has a four-byte unsigned big-endian length followed by its exact bytes. Each kind has a fixed field count. Both sides enforce `checkpoint.MaxFrame` on each frame before allocating the payload. The numeric kinds, field order and decoder live together in [frame.go](internal/frame/frame.go).

Mutation requests carry the canonical bytes from `checkpoint.Intent.Body`. Home writes carry the scoped slot, home public key and detached home and session signatures. Home reads and grant checks sign canonical JSON containing the operation, schema, witness key ID, slot, challenge and receipt ID in the home namespace. Both IDs use 64 lowercase hex digits. An all-zero receipt ID requests current state only.

The witness signs each grant and failure code over its epoch and the SHA-256 digest of the exact length-prefixed request, including the slot, home key and delivery challenge for home operations. The home checks this proof against its independent witness pin. A missing or invalid disposition leaves a delivered mutation unresolved.

A mutation returns one receipt frame. A read returns three ordered frames carrying current state, the fresh signed receipt and the optional historical receipt. Two empty fields in the last frame mean no receipt matched. Each frame fits the same ceiling even when both receipts contain maximum-length identifiers. The client verifies the fresh challenge, slot, guard, epoch and historical evidence before returning the view. A signed inhibited view accompanies `ErrUnavailable`.

The home requires proof of possession of the pinned witness P-256 SPKI with client role usage. Certificate validity dates are ignored. Poll retries peer alerts with jittered backoff capped at 30 seconds. The home reserves four handshake slots for the configured witness source prefixes and permits four others, with a maximum of two per source in each group. Owner admission checks the kernel peer UID before TLS. Platforms without peer credential support refuse owner connections. The first TLS byte must arrive within 500 milliseconds, with five seconds total for the handshake. After authentication the home permits one active poll. The witness reserves two connections per owner listener independently of its serial outbound poll loop. The first frame length must arrive within two seconds. A valid length opens the remainder of the 30-second exchange deadline. Each endpoint charges requests before grant lookup and signature verification. Failure replies pace the next poll with jittered exponential backoff, up to five seconds during repeated refusals. Each endpoint has a rolling limit of 60 calls per minute shared across mutations, current reads and grant checks, plus 60 reads naming IDs in the slot’s committed receipt history. Missing IDs and settlements use the ordinary allowance. Repeated historical reads include current state, so the ceiling is 120 current views per endpoint per rolling minute. Budgets survive reconnects. Closing the listener cancels its workers.

## Lost acknowledgements

The client uses jittered reconnect delays capped at one second on transient connection failures before sending, up to the caller's deadline or 30 seconds. A TLS refusal during owner connection establishment ends that attempt. After mutation delivery, a peer alert cannot establish the outcome. A rejected write that transferred zero mutation bytes returns `link.ErrNotSent`. A broken exchange after a mutation write begins, an unrecognized reply or a receipt that fails `checkpoint.MatchReceipt` leaves the outcome unknown.

Keep the original intent. Reconnect and issue a fresh challenged read with its mutation ID in `ReceiptID`. Verify the prior receipt against the saved intent and compare the current state and fence before publication. An authorized retry of the exact latest mutation can recover the original acknowledgement. A superseded receipt is historical evidence. After uncertain delivery the Endpoint retains the mutation ID and canonical intent digest across reconnects. A missing receipt leaves it pending. A different mutation gets ErrNotSent until an exact retry returns its receipt, a verified recovery read finds the matching receipt, or Settle establishes its disposition. Before submitting a mutation, the home journal persists its canonical intent and the PendingMutation record (ID and checkpoint.RequestDigest of the body), scoped to the slot, witness pin and epoch. Endpoint.PendingMutation returns a copy of the retained record for journaling. After a restart, pass the unresolved record to NewEndpointWithPending for that same enrollment and generation before serving calls. Clear the journal entry only after recording a definitive outcome.

Both the write-granted home and owner can call Settle with the configured epoch, slot and mutation ID. The canonical settlement request binds the expected epoch. Under the mutation commit lock the witness checks that epoch before looking up a receipt or installing a fence. It returns its original receipt, including superseded receipts, or permanently fences the ID and returns a signed ErrNotApplied. A persistent backend must commit the tombstone before answering and consult it in every commit transaction, including work continuing after disconnect. A lost Settle reply can be retried.

For qualification, `linktest.Proxy.Forward` relays one exchange between two authenticated streams. Arm `DropNextReply` before the mutation and close both streams when `Forward` returns. The proxy consumes the complete successful receipt before dropping it, so a subsequent read can establish what committed.
