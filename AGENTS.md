# ataniq

Instructions for coding agents and contributors. `README.md` describes the project and `CONTRIBUTING.md` its workflow.

## Development environment

The targets below are the specification for setting up a checkout.

- Prerequisites: Git, Make, POSIX shell, grep, and a Go bootstrap driver supporting toolchain selection (Go 1.21 or newer). The selected developer toolchain is pinned in `.go-version`; do not copy the exact pin elsewhere.
- The provisional terminal console uses the Bubble Tea v2 Go module and its transitive module dependencies; it needs no additional executable tool. The bootstrap downloads them, the doctor checks them offline, and their notices are in `third_party/terminal-console`. See [the console guide](docs/terminal-console.md).
- The console's terminal toolkit also uses patched copies of the `charmbracelet/x/vt` and `charmbracelet/x/ansi` Go modules, carried in `third_party/patched` as directory replacements in `go.mod` (see each `NOTICE.md`; drop a copy once an upstream release contains its fixes). They need no additional tool and no download. `go mod verify` does not cover directory replacements, so the doctor does not verify these copies: git protects them, and a change to them is a reviewed change. A test checks the `go.mod` entries for them, so do not run `go mod tidy` to change them.
- Preview setup with `make -n bootstrap` and review `scripts/go-tool.sh`, then run `make bootstrap` after reviewing it. It resolves the selected toolchain through Go's verified toolchain mechanism, records its executable in ignored build state, and downloads module dependencies, using process-local settings. It is idempotent and needs no root. Repeat it if the pin or resolved executable changes; an already-exact driver works without the record.
- Verify a checkout: `make doctor`. It prints one line per item, except that a Go diagnostic (or `(no diagnostic from go)`) is printed indented above a `fail` line, and exits non-zero when something is missing: a line starting `missing`, `fail` or `error` is a problem, a line starting `expected` is a known failure that is accepted. It checks the tools and the selected toolchain, and checks offline that every package and test, for the host platform, loads from the module cache with hashes matching `go.sum` and that cached modules are unchanged since download. It prints the Go diagnostic, which names the failing module when the failure is in a module; a missing module is repaired by `make bootstrap`, a checksum mismatch by restoring `go.sum`, or by running `chmod -R u+w` on the named module directory in the module cache, removing it and running `make bootstrap`, a modified module in the same way, and any other load error by fixing the failing package. It also checks that `grep` is installed, which the Go helper uses. When it is not, doctor prints `missing: grep` and skips the Go checks, and bootstrap, test and build stop with `missing: grep`. Run it before the tests and after pulling.
- Tests: `make test` runs the offline whole suite, which includes the patched modules' own tests (`make test-patched` runs only those; `./...` does not reach directory replacements, so they are tested by package name from the main module: x/vt, x/ansi and its `parser`, `kitty` and `iterm2` subpackages; the x/ansi `sixel` subpackage is left out because it needs a module that is not cached); `make test-dev` runs the targeted development-tooling checks; `make test-canary` runs the tests of code behind the `ataniq_canary` build tag, over every package that holds a Go file whose build constraint names it (found by grep at run time), and over `./tests/` only when no package is tagged, so that `go test` never gets an empty list. `./tests/`, which holds the checks of the tag, runs once per suite, untagged, in `make test`: its checks run `go list` with the tags they need, and `TestCanaryTagTestsClosure` fails when a file its tests build has a build constraint that names either tag, or when the source inputs its test closure selects (Go and non-Go files, and each package's cgo flags and pkg-config names) differ under any of the four tag sets from the untagged ones, so running it under a tag again is a deliberate change, and `TestNoGoFileStartsWithBOM` refuses a Go file that begins with a byte-order mark, after which the tagged runs' grep does not see a build constraint (the targeted check of the tag is `sh scripts/go-tool.sh test ./tests/ -run CanaryTag`). `make test` stays untagged and skips that code, so while tagged code exists the whole suite is `make test` and then `make test-canary`, which CI runs as its second job. `make canary-build` is the one target that builds binaries with the canary tag alone; no release and no CI job uses it. `make test-ownerchannel` runs the tests of code behind the `ataniq_ownerchannel` build tag, the owner channel's, in two runs: with that tag alone and with it and `ataniq_canary` together (no other target tests the pair), each over every package that holds a Go file whose build constraint names a tag it sets (found by grep at run time), and over `./tests/` only when that run has no such package; CI runs it as its third job, naming the target and never the tag, and no release uses the tag; `make ownerchannel-build` is the one target that builds a binary with that tag alone, only the daemon, into `build/owner/` (ignored), for the owner's own trial of the unqualified channel: it runs doctor first and starts nothing, no release, no CI job and no other target uses or depends on it; `make scratch-seat-build` is the one target that builds the daemon with both tags (`ataniq_ownerchannel,ataniq_canary`), only the daemon, into `build/scratch-seat/` (ignored), for the owner's own trial of real scratch leads with the seat gate: it runs doctor first and starts nothing, no release and no CI job uses it, and no other target uses or depends on it; the guard test refuses any recipe but these three that names the tag, and holds the recipe of `make scratch-seat-build` to exactly its mkdir and its one build, with `doctor` its sole prerequisite (the targeted check is `sh scripts/go-tool.sh test ./tests/ -run OwnerChannelTag`). While code behind that tag exists the whole suite is `make test`, `make test-canary` and `make test-ownerchannel`. All test targets run doctor first. Offline disables dependency and toolchain acquisition; it does not confine the trusted Go executable or change host telemetry policy.
- On Linux, `make home-build` runs doctor and builds only `cmd/ataniq-home` into `build/home/`. It starts nothing. The targeted check is `sh scripts/go-tool.sh test ./cmd/ataniq-home/... ./tests/` after doctor. See the [home identity ceremony](docs/home.md).
- Static qualification artifacts: `make qualification-host-build` uses the same selected offline Go wrapper to build the Linux/amd64 probe and explicit host driver. Targeted checks are `sh scripts/go-tool.sh test ./qualification/host/... ./tests/...` after doctor. Existing systemd/bubblewrap/BPF subjects are explicit coordinator-only qualification inputs, not installed developer prerequisites; ordinary tests never launch services or namespaces. See [the host manual](docs/qualification-host.md).
- Lead sandbox qualification artifacts: `make qualification-leadsandbox-build` runs doctor and uses the same selected offline Go wrapper to build the static Linux/amd64 probe `build/ataniq-probe` (from `cmd/ataniq-probe`) and the opt-in harness `build/qualification-leadsandbox`; building them starts nothing. pasta and bubblewrap are explicit coordinator-only qualification inputs, not installed developer prerequisites; ordinary tests never launch them. See [the lead sandbox qualification manual](docs/qualification-lead-sandbox.md).
- Canary run kit: `make canary-build` runs doctor and uses the same selected offline Go wrapper to build, with the `ataniq_canary` tag, into `build/canary/` (ignored), the binaries the attended canary run uses: `ataniqd`, `ataniq-holder`, `ataniq-canary`, `ataniq-canary-standin`, `ataniq-console`, `ataniq-intake` and `ataniq-probe` (the stand-in and the probe static); building them starts nothing. The run script `qualification/canary/run/canary-run.sh` starts a real unit, sandbox and agent and is run only by the owner's hand with the lead present: never run it without `--dry`, which prints every step and starts nothing, or `--self-test`, its test entry, which only computes and prints. `qualification/canary/run/canary-reset.sh` also deletes directories (the `state/` and `runtime/` of a prepared root) after a word the owner types, and is run only by the owner's hand, never by an agent and never with its word typed for the owner: its only agent-safe forms are `--dry` and `--self-test`. `qualification/canary/run/canary-prepare.sh` writes files and folders under the cache folder and is run by an agent only with `--dry` (or `--self-test`). `qualification/scratch-seat/prepare.sh`, of [the attended proof of real replies](docs/scratch-seat-proof.md), is run by an agent only with `--dry` or `--self-test`; its `--write` and `--status` are the owner's (`--write` writes the proof's own folder; `--status` runs the daemon's `run --scratch CONFIG --owner-channel --seat-gate ADDR --owner-settings DIR --check` on his trial's state folder, which binds, locks and starts nothing but reads his folders, and with `--record` writes the baseline of step g into the proof's own `evidence/step-g`), and so is the `ROOT/netcheck.sh` its `--write` writes, which starts pasta, bubblewrap and a throwaway user unit; its tests run those modes only in private sample folders with stub binaries, and its targeted checks are `sh scripts/go-tool.sh test ./tests/ -run ScratchSeat`, `sh scripts/go-tool.sh test -tags ataniq_ownerchannel,ataniq_canary -run 'ScratchSeat|OwnerSettings|KeysCheck|ScratchLeadReach' ./cmd/ataniqd/ ./internal/leaddaemon/`, `sh scripts/go-tool.sh test -tags ataniq_canary -run BindTable ./internal/leadholder/sandboxstart/` and `sh scripts/go-tool.sh test -tags ataniq_ownerchannel -run 'TheScratchSettings|VerifyKeys' ./internal/approval/hostadapter/ ./internal/approval/ownerjournal/` after doctor. `ROOT/netcheck.sh` (written by `canary-prepare.sh --pass B`) starts pasta, bubblewrap and a throwaway user unit and makes four unauthenticated requests, and is run only by the owner's hand, never by an agent. pasta, bubblewrap and systemd are explicit owner-only inputs of that run, not installed developer prerequisites; ordinary tests never launch them. The targeted check is `sh scripts/go-tool.sh test ./tests/ -run CanaryRunKit` after doctor. See [the run kit's guide](qualification/canary/run/README.md).
- Scratch leads: the lead control plane (`ataniqd run --scratch CONFIG`, the desk's `ataniqd chat list|set` of the leads' written replies, the owner's `ataniq-canary scratch-init` and `scratch-clean`, and the console's leads view) is code behind the `ataniq_canary` build tag, in `internal/leadcontrol` (the command table, no untagged file), `internal/leadchat` (the replies' store, no untagged file) and the tagged files of `internal/leadcanary` (the reply folder and instruction text in `provision/chat.go` and `provision/instructions.go`), `internal/leaddaemon` (the chat in `chat_desk_linux.go`, `chat_port_linux.go` and `chat_cli_linux.go`), `cmd/ataniqd` and `cmd/ataniq-canary`, so `make test-canary` covers it, `make test` skips it and `make canary-build` builds its binaries (`make scratch-seat-build` builds the daemon with it and the owner channel, for the owner's trial with the seat gate); the wire values (`internal/leadwire`), the console's client (`internal/consoleclient`), the leads view (`internal/terminalconsole/leadctl`) and `cmd/ataniq-console` carry no tag. The targeted checks are `sh scripts/go-tool.sh test -tags ataniq_canary ./internal/leadcontrol/ ./internal/leadchat/ ./internal/leadcanary/... ./internal/leaddaemon/ ./cmd/ataniqd/ ./cmd/ataniq-canary/` and, untagged, `sh scripts/go-tool.sh test ./internal/leadwire/ ./internal/consoleclient/ ./internal/terminalconsole/... ./cmd/ataniq-console/`, after doctor. See [the scratch leads guide](docs/scratch-leads.md).
- AI host hardening: `deploy/ai-host/ap14-level1.sh` (AP14 level 1) is a read-only check: it runs `sudo -n -l -U NAME` and judges only what sudo prints (a `NOPASSWD` command, `targetpw`, `rootpw`, `runaspw`, `!authenticate`, `exempt_group`, a non-zero or missing `timestamp_timeout=0`), checks the root-owned standing-grants register `/etc/ataniq/grants` by simple stat rules, and prints plain steps for the owner; it changes nothing. The owner makes every change by hand, from the steps of its README: the edits with `visudo -f`, the drop-in `/etc/sudoers.d/zz-ap14-level1-NAME` and the register. It is run only by the owner's hand, as root, in host sitting A: an agent runs it only with `--self-test`, never with `--check` (it runs sudo as root). What an agent may run is exactly `sh deploy/ai-host/ap14-level1.sh --self-test` (optionally with `--fixtures DIR --user NAME` or `--register-tree DIR`), which runs unprivileged, reads the fixture cases in `deploy/ai-host/self-test/` (or the case or tree DIR) in place, never runs sudo and writes nothing, and the Go tests of `./tests/`, which run `--self-test` on cases and trees in temporary folders and run `--check` only where it is refused on its arguments. The targeted check is `sh scripts/go-tool.sh test ./tests/ -run AiHost` after doctor. See [the AI host guide](deploy/ai-host/README.md).
- Changelog: a user-visible change adds `changelog.d/<section>-<slug>.md` in the same commit (see `changelog.d/README.md`) and does not edit `CHANGELOG.md`; `make changelog-fold ARGS='--into <version>'` (add `--dry-run` to ARGS to preview) and `make changelog-check` are release and hotfix steps, run as the first fix commit on the release branch after `qargi release start <version>` (add `--allow-empty-notes` when the release's entries are all fragments, since `[Unreleased]` is then empty and the start is refused otherwise) and before `qargi release push`, and need no Go toolchain. The targeted check is `sh scripts/go-tool.sh test ./tests/ -run Changelog` after doctor.
- Never run the bootstrap on a checkout you have not reviewed; read the preview first.
- When the project needs a new tool, add it to the bootstrap, to the doctor and to this list in the same change.
